# SEC-001 批量包 64MB 主线程同步解压无限制（DoS） 【P0】

## 是什么

客户端发来的 BatchPacket（批处理包）在**主线程**上同步 zlib 解压，解压上限为 64MB，且没有任何速率限制、解压预算或每 tick 配额。

关键代码位置：

- `src/pocketmine/network/compat/BatchCodec.php:35`
  ```php
  const MAX_PAYLOAD = 67108864; // 64MB
  ```
- `src/pocketmine/network/compat/BatchCodec.php:41`
  ```php
  return zlib_decode($payload, self::MAX_PAYLOAD);
  ```
- 调用入口 `src/pocketmine/network/Network.php:235`（`processBatch`）和 `Network.php:281`（`processProtocol011Batch`），两者都在主线程 `tickProcessor` 的包处理流程内同步执行。
- 另一处同类问题：`src/pocketmine/network/protocol/v84/LoginPacketV84.php` 的 `decode()` 中
  ```php
  $str = zlib_decode($this->get($this->getInt()), 1024 * 1024 * 64);
  ```
- 第三处：`src/pocketmine/Player.php:2632`（`isMinimalProtocol015BootstrapBatch` 中同样 64MB 解压）。

## 为什么

1. **压缩炸弹放大比**：zlib 的解压膨胀比在精心构造的输入下可达 1000:1 以上。攻击者只需发送几 KB 的压缩包，服务端就要在主线程解出 64MB 并遍历，单次即可造成数百毫秒到数秒的主线程停顿。
2. **主线程停顿 = 全服卡顿**：这个核心是单主线程 tick 架构（`Server::tickProcessor`），主线程卡住意味着所有玩家的 tick、区块、实体全部冻结。循环发送即可让全服持续卡死，且不需要任何认证（登录前即可触发）。
3. **每玩家可叠加**：没有 per-player/per-tick 配额，N 个连接同时发送，CPU 线性放大。
4. 0.11 路径（`processProtocol011Batch`）与 0.15 引导路径（`isMinimalProtocol015BootstrapBatch`）同样无限制，三条路径都要修。

## 怎么做

1. **降低单包解压上限**：`BatchCodec::MAX_PAYLOAD` 从 64MB 降到 4MB（实际合法批包——约几十个区块+实体包，压缩后极少超过 1MB；4MB 留足余量）。`LoginPacketV84` 的解压上限降到 1MB（登录 JWT 链实际只有几 KB）。
2. **增加每 tick 每玩家解压预算**：在 `Player` 上加一个本 tick 已解压字节数计数器（如 `batchDecompressedBytesThisTick`），`processBatch` 解压前检查，超过预算（如 8MB/tick）直接丢弃该包并计数；每 tick 开始时清零（可在 `Player::onUpdate` 里做）。
3. **解压前先查原始长度**：`$packet->payload` 超过某个原始上限（如 1MB 压缩后）直接拒绝，不解压——合法客户端的批包压缩后远小于此。
4. **失败/超限计 attack 计数**：连续超限 N 次调用已有的封禁/IP 屏蔽机制（`RakLibInterface` 里已有 `Scaxe_Block_` 防火墙屏蔽先例可复用）。
5. 三条路径（`processBatch`、`processProtocol011Batch`、`isMinimalProtocol015BootstrapBatch`）统一收敛到 `BatchCodec::decompress` 一个入口，在入口内做全部限制，避免漏改。

## 怎么测

- **单元级**：写测试脚本构造 zlib 炸弹（`zlib_encode(str_repeat("\0", 64 * 1024 * 1024), ZLIB_ENCODING_DEFLATE, 9)`，压缩后仅约 60KB），封装成 BatchPacket payload 发给本地起的服务端。修复前：主线程可观测到秒级卡顿（用 `/timings` 或 tick 时间日志确认）；修复后：包被直接丢弃，tick 时间无波动，日志出现丢弃/超限记录。
- **集成级**：用 Python 脚本模拟 RakLib 客户端（tests/ 目录已有 console-reader-pty.py 等 socket 脚本先例），单连接循环发压缩炸弹 100 次/秒，持续 30 秒。验收标准：期间其他客户端 ping 延迟与 tick 时间（`/status`）保持正常（tick < 50ms）。
- **回归级**：正常客户端（0.11/0.14/0.15 三协议各一）登录、加载区块、跑图、传送，确认合法批包不受新限制影响（重点测大量区块同时加载的场景，如传送 1000 格外后回城）。
- **压力回归**：`isMinimalProtocol015BootstrapBatch` 的 1MB 限制不得误杀 0.15 引导批包——用一个真实 0.15 客户端完整登录一遍。

# SEC-002 RCON 全客户端共享单一命令/响应槽（竞态） 【P0】

## 是什么

RCON 服务端（`src/pocketmine/network/rcon/RCONInstance.php`）为最多 50 个客户端分配了独立的 socket 槽位（动态属性 `{"client".$n}`），但**命令输入 `$this->cmd` 和响应 `$this->response` 是全类各只有一个**。所有客户端的命令读写共享同一对槽位。

关键代码位置：

- `RCONInstance.php:172-183`（命令处理）：
  ```php
  $this->cmd = ltrim($payload);                       // 全局唯一 cmd 被覆盖
  $this->synchronized(function(){ $this->waiting = true; $this->wait(); });
  $this->waiting = false;
  $this->writePacket($client, $requestID, 0, str_replace("\n", "\r\n", trim($this->response)));
  $this->response = "";
  $this->cmd = "";
  ```
- `RCONInstance.php:144-147`：死代码——`$this->response = "[INFO] Successful Rcon connection from: /$addr:$port";` 紧跟下一行 `$this->response = "";` 立即覆盖。
- `RCONInstance.php:138-141`：`serverStatus` 反序列化处顺带发现 `unserialize` 加固不一致问题（见 SEC-005）。

## 为什么

1. **正确性 bug**：两个客户端同时连 RCON 时，A 发命令 → 主线程消费 `$this->cmd` → B 发命令覆盖 `$this->cmd` → A 收到的是 B 命令的执行结果，B 的响应可能被 A 的空响应覆盖。命令错配对运维是灾难（想象 A 执行 `stop`，B 执行 `say hello`，响应互相串）。
2. **`wait()` 无超时**：如果主线程没在处理 RCON（极端情况），RCON 线程会永久阻塞在 `$this->wait()` 上，所有后续客户端的命令全部排队卡死。
3. **`$this->response` 是无界共享缓冲**：命令输出没有按客户端隔离，长输出会被并发的其他客户端读走或截断。
4. 顺带问题：密码比较用 `===` 明文比较存在理论上的计时侧信道（低危，顺手改 `hash_equals`）；50 个客户端用动态属性管理在 pthreads 环境下有额外序列化开销，且是反模式。

## 怎么做

1. **按客户端索引隔离命令与响应**：把 `$this->cmd` / `$this->response` 改为数组，按槽位 n 存取：
   ```php
   $this->{"cmd" . $n} = ltrim($payload);
   $this->{"response" . $n} = ...;
   ```
   或者更彻底：把 50 个客户端槽位重构为一个 `RconClient` 值对象数组，持有 socket、status、timeout、cmd、response 字段。
2. **给 `wait()` 加超时**：`$this->wait()` 改为 `$this->wait(5000)`（5 秒），超时后向客户端返回错误响应而不是永久阻塞。
3. **登录成功那行死代码删除或恢复语义**（当前两行互相矛盾，删掉第一行）。
4. **密码比较改 `hash_equals($this->password, $payload)`**（注意 `hash_equals` 要求两个参数都是 string，对 `$payload` 先做 `is_string` 检查）。
5. （可选，P2）动态属性槽位重构为对象数组；注意 pthreads 环境下数组元素若为对象需要可序列化，逐项确认。

## 怎么测

- **并发正确性测试**：写脚本同时开两个 RCON 连接，交替发送不同命令（如 `list` 和 `version`），断言每个连接收到的响应与它发送的命令对应（`list` 的响应含玩家数格式、`version` 的响应含版本号）。修复前可复现响应串线；修复后 100 轮无错配。
- **阻塞超时测试**：RCON 线程发命令后人为挂起主线程消费（如临时在消费侧加 sleep 10 秒），确认 5 秒后客户端收到超时响应、线程不永久卡死、后续命令可继续处理。
- **回归测试**：单客户端 RCON 全流程——登录（对/错密码）、执行 `list`/`say`/`stop`，行为与修复前一致；错密码后连接被置 -1 断开。
- **计时侧信道**：无需专门测（低危），改完后用 `php -r` 确认 `hash_equals` 在该 PHP 7.3 构建可用即可。

# SEC-003 登录认证空转：JWT 验证结果无人消费 【P1】

## 是什么

两条认证链路都是摆设：

1. **Player 层**：`src/pocketmine/Player.php:2347`
   ```php
   public function onPlayerPreLogin(){
       //TODO: implement auth
       $this->tryAuthenticate();
   }
   public function tryAuthenticate(){
       //TODO: implement authentication after it is available
       $this->authenticateCallback(true);   // 永远 true
   }
   ```
2. **协议层**：`src/pocketmine/network/protocol/v84/LoginPacketV84.php` 的 `decode()` 实现了完整的 Mojang JWT 证书链验证（`MOJANG_PUBKEY` + `decodeToken` + 链式 key 传递），算出 `$verified`，但**全仓库没有任何代码读取这个 `$verified` 来拒绝未通过验证的玩家**。验证结果被静默丢弃。

更严重的是这套验证本身可被绕过：`decode()` 的链式逻辑里，只要攻击者提交的 token 带一个非 Mojang 的 `identityPublicKey`，`$chainKey` 就会被替换成攻击者的公钥（`LoginPacketV84.php:76-79` 的 "Looped key chain" 分支），后续 skin token 用攻击者自己的私钥签名即可通过验证。

## 为什么

1. **身份冒充**：用户名、UUID 完全由客户端声明且无任何校验。攻击者可冒充任意已存在玩家（包括 OP）的名字登录。虽然 `processLogin` 会踢掉重名在线玩家，但离线玩家的 NBT 数据（背包、位置、权限插件记录）会按名字匹配——配合权限类插件即等于拿到任意玩家权限。
2. **白名单/封禁体系建立在不可信的身份上**：`processLogin` 的 whitelist / ban 检查都基于客户端自报的名字与 IP，名字可随意更换，封禁形同虚设（只挡 IP 有意义）。
3. **虚假安全感**：`LoginPacketV84` 里那一大段 JWT 验证代码让维护者以为"我们有认证"，实际上它是装饰。要么真用，要么删掉，最怕的是留着。
4. **绕过路径明确**：如上所述，自签 key 的链式替换让"验证通过"可被任何攻击者伪造，即使未来有人开始消费 `$verified`，不修链式逻辑也挡不住。

## 怎么做

本核心定位是 0.11–0.15 老协议离线服（Xbox Live 认证在这些版本上本就不可用），所以**推荐方案 A 而不是补认证**：

**方案 A（推荐）：明确离线模式，移除假验证**
1. 删除 `LoginPacketV84::decode()` 中整段 JWT 链验证（约 80 行），`username` 直接从明文字段或 token payload 读取，`identityPublicKey` 字段删除。
2. `Player::tryAuthenticate` 里加一行注释说明这是有意的离线模式决策（引用本文件编号 SEC-003），避免后人再"修复"它。
3. 在 `server.properties` / 文档中明确标注此核心只支持离线模式，并建议服主用白名单 + 插件登录系统（Auth 类插件）补偿。

**方案 B：真消费 `$verified`（不推荐但列出）**
1. 先修 SEC-004 的全部解析崩溃面与 DER 编码 bug。
2. 修链式 key 替换漏洞：`identityPublicKey` 必须等于 `MOJANG_PUBKEY` 才允许更新 `$chainKey`，否则 break。
3. `Player` 收到 LoginPacketV84 后检查 packet 上的 `verified` 标志，false 则 `close("", "disconnectionScreen.invalidSession")`。
4. 提供 `server.properties` 开关（`online-mode=`，默认 false），让服主可选开启。

无论 A/B，都要做：**uuid/name 一致性记录**——为防冒充，在玩家数据目录记录 name → 首次出现时的 clientId/UUID，后续不匹配时告警（仅告警，不硬踢，避免误伤）。

## 怎么测

- **方案 A 测试**：仓库全局 grep 确认 `MOJANG_PUBKEY`、`decodeToken`、`openssl_verify` 已无引用；真实 0.14/0.15 客户端登录正常；`grep -rn "tryAuthenticate" src/` 确认调用链清晰。
- **方案 B 测试**：
  - 正向：正版客户端（或用合法 JWT 工具链构造的模拟器）登录成功。
  - 反向 1：用自签名 key 构造 JWT 链（模拟链式替换攻击）→ 必须被拒绝，`invalidSession` 断开。
  - 反向 2：过期时间戳（`exp` < now）的 token → 必须被拒绝。
  - 反向 3：签名被篡改一个字节的 token → 必须被拒绝。
- **冒充防护验证**：记录机制——用两个不同 clientId 用同名登录，确认第二次触发告警日志。

# SEC-004 LoginPacketV84 解析链路脆弱（空指针 / 段数 / DER 长度编码错误） 【P1】

## 是什么

`src/pocketmine/network/protocol/v84/LoginPacketV84.php` 有三个独立的解析缺陷：

1. **空指针链**（第 54 行）：
   ```php
   $chainData = json_decode($this->get($this->getLInt()))->{"chain"};
   ```
   `json_decode` 对畸形 JSON 返回 `null`，对 `null` 取属性在 PHP 7.3 产生 Notice 并返回 null，随后 `!empty($chainData)` 为 false 走 else 分支 `unset($chainData[$index])`——`$index` 在此作用域可能未定义，行为未定义。
2. **JWT 段数不校验**（`decodeToken` 第 115 行）：
   ```php
   list($headB64, $payloadB64, $sigB64) = $tokens;
   ```
   token 少于 3 段时产生 Undefined offset 错误，`$sigB64` 为 null 传入后续 base64_decode。
3. **DER 长度编码 bug**（`decodeToken` 第 125-135 行）：
   ```php
   if($len > 255){
       throw new \RuntimeException("Invalid signature format");
   }elseif($len >= 128){
       $derSig .= chr(81);   // BUG: 应为 chr(0x81)
   }
   ```
   ASN.1 DER 中 128–255 长度的长格式首字节是 `0x81`（表示"后续 1 字节是长度"），`chr(81)` 是十进制 81 = 十六进制 0x51，编码完全错误。长度落在该区间的合法签名会验证失败。（注：ES384 签名实际长度通常固定，此 bug 平时潜伏，但一旦触发即为逻辑错误。）

## 为什么

1. **登录前的崩溃面**：这些都发生在登录包解码阶段，任何客户端（无需认证）都能发送畸形包触发。虽然异常被上层 `processBatch` 的 try/catch 兜住不至于崩服，但会产生异常堆栈日志噪音，且解码失败路径未定义行为多。
2. **`$index` 未定义的 unset** 是真实 UB：依赖 PHP 版本与错误报告级别，可能在严格配置下升级为异常。
3. **DER bug 说明这段代码从未被真正测试过**——它与 SEC-003 互相印证：验证结果没人消费，所以错了也没人发现。

## 怎么做

1. 空指针：先判空再取属性：
   ```php
   $decoded = json_decode($this->get($this->getLInt()), true);
   $chainData = (is_array($decoded) && isset($decoded["chain"])) ? $decoded["chain"] : [];
   ```
   同步把后续对 `$webtoken` 的数组访问检查补齐（改用 `json_decode(..., true)` 数组风格可一并消除对象属性 Notice）。
2. 段数：
   ```php
   $tokens = explode(".", $token);
   if(count($tokens) !== 3){ return array(false, null); }
   ```
3. DER：`chr(81)` → `chr(0x81)`。
4. 若采用 SEC-003 方案 A（删除整段验证），本条目 1/2/3 随之消失，无需单独修——**推荐把本条与 SEC-003 一起处理，避免修一个即将删除的函数**。

## 怎么测

- 构造畸形登录包（可用 PHP 脚本手工拼二进制）：
  - chain 字段传非 JSON 字节串 → 修复后应安静拒绝（返回 false 链），无 Notice/Warning。
  - JWT 传 "aaa"（无点分段）→ 修复后返回 `(false, null)`，无 Undefined offset。
  - 签名长度恰为 128–255 区间的 DER 编码向量 → 用 `openssl_verify` 直接单元测试 `decodeToken` 的 DER 重组段（把该段抽成静态方法便于测试），对比 `openssl_verify` 对标准 DER 的接受结果。
- 回归：正常 0.14/0.15 客户端登录无异常（若走 SEC-003 方案 A，此测试改为客户端正常登录即可）。

# ARCH-003 pthreads 线程边界隐患（autoload 不继承等） 【P2】

## 是什么

pthreads 架构下子线程不继承主线程的 `spl_autoload_register`。`src/pocketmine/PocketMine.php:122` 的注释直接承认了这一点："子线程不会继承 spl_autoload_register，预先加载日志级别接口与格式化类，避免线程内记录日志时找不到 LogLevel / TextFormat"。近期 git 历史有三个 commit 都在修这类线程边界问题（`c45f9ac` Fix LogLevel autoload in worker threads、`8d172f3` Serialize deferred tiles for pthreads、`2d67936` Preload TextFormat for console thread）。

## 为什么

1. **无底洞模式**：每往 AsyncTask/Thread 里传一个新类型的对象或让线程内触发一次新的类加载，就可能复现"类找不到"崩溃，而且是低概率、难复现的崩溃。
2. **静默数据丢失**：pthreads 对不可序列化的属性静默丢弃（如 `8d172f3` 修的 deferred tiles），不报错，出 bug 时极难定位。

## 怎么做

1. **建立预加载清单**：集中管理所有线程内会用到的类，在 `PocketMine.php` 现有预加载处（122 行附近）统一 `class_exists(..., true)` 一遍；新增线程内代码时清单必须更新，并在 HANDOFF.md 记录此约定。
2. **线程任务数据规约**：所有 `AsyncTask` 子类携带的数据必须是标量/数组/明确的可序列化对象；在 code review checklist 写明。可写一个静态检查脚本 `tests/check-thread-data.php`，扫描 AsyncTask 子类的 public 属性类型注释。
3. 长期（PHP 7.4 / PM4 迁移时）考虑用 pmmpthread/线程外进程替代，但当前版本下只做 1/2。

## 怎么测

- 压测复现：多玩家大范围跑图（触发大量 GenerationTask/LightPopulationTask）+ 同时使用 RCON/控制台日志，运行 30 分钟，监控 worker 线程崩溃日志（"Class ... not found" 应为零）。
- 新增线程代码时：在 worker 线程入口故意 `var_dump(get_declared_classes())`（调试模式）确认关键类已加载。

# BUG-001 processLogin 对首次登录玩家做 null 算术 【P2】

## 是什么

`src/pocketmine/Player.php:2424`：
```php
$nbt = $this->server->getOfflinePlayerData($this->username);
$this->playedBefore = ($nbt["lastPlayed"] - $nbt["firstPlayed"]) > 1;
```
首次登录的玩家其 `lastPlayed` / `firstPlayed` tag 可能尚不存在（`getOfflinePlayerData` 对新玩家生成默认 NBT，是否含这两个键取决于实现路径），null - null = 0，`playedBefore = false`——恰好结果碰巧正确，但这是**靠 PHP 宽松语义碰运气**。

## 为什么

`Zenith.phar`（5854673 字节）与 `Zenith-v0.3.1.phar`（5856571 字节）作为构建产物被提交进 git 仓库。

## 为什么

1. 构建产物属于发布物（GitHub Release），不属于源码仓库；每次重新构建都会产生新的二进制 diff，仓库体积单调膨胀。
2. 旧版本 phar（v0.3.1）夹带历史代码，有安全审计盲区（若有人误部署旧 phar，本审计结论不适用）。

## 怎么做

```sh
git rm --cached Zenith.phar Zenith-v0.3.1.phar
echo '*.phar' >> .gitignore
```
发布时用 `gh release upload` 或手动上传到 GitHub Release 附件，不打进源码历史。（可选）若要从历史中彻底清除以缩减 clone 体积，用 `git filter-repo`——注意需要强推并协调所有协作者，当前仓库 pack 仅 5.72MB，收益有限，可不做。

## 怎么测

- `git ls-files | grep '\.phar$'` 为空；CI/发布流程中确认 phar 从构建脚本生成并上传 Release。
- `start.sh` 启动脚本不依赖仓库内 phar（grep 确认）。

# HYG-003 分支丛林：本地 13 个 / 远程 15 个分支 【P2】

## 是什么

本地分支：chunk-disappear、chunk-fix、explore/anticheat、feat/gorigional-generator、feature/console-input、main、other-issues、port/lycore-gameplay、port/lycore-structures、pre-rebase-main、refactor/protocol-compat 等 13 个；远程另有 protocol-upgrade、feature/multi-world-gamerule、feature/structure-generation、feature/villager-trade 等。`chunk-disappear` 与 `chunk-fix` 分支的存在表明区块消失 bug 是靠开分支救火的，修复是否已回流 main 无从追溯。

## 为什么

1. 长期不合并的分支会腐化（与 main 的冲突越来越大，最终永远合不进去）。
2. `pre-rebase-main` 这类分支名表明 rebase 过但旧指针没清理，历史考古成本高。
3. AI 交接工作流（HANDOFF.md）下，分支越多，下一个会话越难判断"哪个分支是权威"。

## 怎么做

1. 逐分支核对：已合并进 main 的删除（`git branch --merged main`）；未合并但有价值的开 issue 记录后删除；`pre-rebase-main` 直接删。
2. 约定主干模式：main 为唯一权威，feature 分支合完即删，长期分支（如 feat/gorigional-generator 已合入的工作）确认后清理。
3. 把分支约定写入 HANDOFF.md，供后续 AI 会话遵守。

## 怎么测

- `git branch --merged main | wc -l` 与 `git log main --oneline | wc -l`（243）对照，删除后确认 main 的关键修复 commit 都在（抽查 chunk-fix 分支的 commit message 是否能在 main `git log --grep` 找到）。
- 删除后三协议客户端登录回归（main 应不受分支清理影响，这是健全性确认）。

# HYG-004 零自动化测试，生成器回归靠人工对比 【P2】

## 是什么

`tests/` 目录只有 2 个手工脚本（console-input.php、console-reader-pty.py），无任何自动化测试框架、无 CI。HANDOFF.md 明确记录：gorigional 生成器移植的性能优化（记忆化、LCG 特化、噪声内联）是靠"优化后输出与优化前逐块一致（方块计数、群系分布、高度范围）"人工验证的。约 100 个新生成器 PHP 文件无回归基线。

## 为什么

1. **生成器是纯函数**（输入种子/坐标 → 输出方块），是最适合快照测试的场景，现在却靠人肉。
2. 下次任何人对生成器/网络协议/物品逻辑的修改都是盲改；bugs.txt 里连续的 bug 组（#001~#003）说明回归已经开始循环。
3. PHP 7.3 + pthreads 的环境特殊性让"本地跑不起来就猜"的概率上升，测试能兜底大部分静态可验证的逻辑。

## 怎么做

分三层，从性价比最高的开始：

1. **生成器快照测试**（最优先）：脚本对固定种子 + 固定坐标集调用 `Gorigional`（及 Normal）生成器，把输出方块序列 hash 成快照文件存 `tests/snapshots/`。任何改动跑一遍对比。用 Termux 环境直接 `php tests/generator-snapshot.php` 即可。
2. **纯逻辑单测**：不需要 pthreads 的类（BatchCodec 的 framed 解析、Binary 读写、ProtocolCapabilities 前缀路由、Config YAML 解析、TextFormat）用简单断言脚本覆盖，不引入重型框架（PHP 7.3 环境装 PHPUnit 也行，但自写 runner 更轻）。
3. **CI**：仓库在 GitHub，加一个 GitHub Actions workflow（php -l 全量语法检查 + 快照测试），push 即跑。

## 怎么测

（本条目本身就是"怎么测"的规划，验收标准如下）
- `tests/generator-snapshot.php` 首次运行生成基线；改动后运行输出 "PASS"（hash 一致）或输出具体哪个区块哪个坐标不一致。
- CI 在 GitHub Actions 上绿（php -l + 快照）。
- 故意改一行 ImprovedNoise 的 lerp 实现验证快照测试能抓住差异（自测试测试）。

# TRIM-007 调试命令加 /debug 前缀归类（保留功能） 【P2】

## 是什么

一组开发/调试用途的命令目前以正常命令形态注册在 `SimpleCommandMap.php`，对所有玩家/控制台可见：

- `CaveCommand`（"cave"，334 行，绕过生成器手动生成洞穴）
- `ChunkInfoCommand`（"chunkinfo"，`SimpleCommandMap.php:131`）
- `LvdatCommand`（"lvdat"，131 行）
- `DumpMemoryCommand`（"dumpmemory"，183 行）
- `GarbageCollectorCommand`（"gc"，182 行）
- `EmojiCommand`（"emoji"，177 行）

**决策：这些命令保留不删**（开发期有用），但统一加 `/debug` 前缀归类，与正常运维命令区分。

## 为什么标注为要调整（而不是删除）

1. 调试命令在核心开发期（生成器调试、内存排查）是刚需，删了还得临时加回来。
2. 但它们目前混在正常命令列表里：`/help` 全量暴露，玩家可感知；个别命令（cave 直接改区块、dumpmemory 暴露内存布局）在错误手里有信息泄露/世界破坏风险。
3. `cave` 这类绕过生成器直接写区块的命令，与 gorigional 生成器的区块状态天然冲突（生成器可能后续覆盖或产生不一致），只应作为显式调试工具存在——前缀化后语义清晰。

## 怎么做

1. **命令改名**：注册名统一加 `debug` 前缀——`SimpleCommandMap.php` 中：
   - `new CaveCommand("cave")` → `new CaveCommand("debug cave")`（若 CommandMap 不支持空格别名，则改为 `debugcave` 并把命令类内 `getName()`/usage 同步改，或改用子命令式实现）
   - 同理：`chunkinfo` → `debugchunkinfo`、`lvdat` → `debuglvdat`、`dumpmemory` → `debugdumpmemory`、`gc` → `debuggc`、`emoji` → `debugemoji`
2. **权限收紧**：这些命令的 `getPermission()` 统一设为 `pocketmine.command.debug`（新权限，默认只授予 OP 且不从配置继承给普通玩家）。
3. **usage 更新**：每个命令类的 `$usageMessage` 与语言文件里的 usage 键同步改名，`/help` 中显示新名。

# MISS-001 缺失：Watchdog 主线程卡死检测 【P1】

## 是什么

现代 PocketMine（1.6.2+）都有 `WatchdogThread`：监控线程每秒检查主线程心跳时间戳，卡死超过阈值秒数时 dump 所有线程堆栈并报告（可选自动重启）。**本核心完全没有这个机制**（全局 grep "watchdog" 无结果）。

主线程单 tick 架构（`Server::tickProcessor`）下，任何主线程阻塞（SEC-001 解压炸弹、SEC-002 RCON `wait()` 永久阻塞、生成器死循环、插件死循环）都表现为"所有人掉线 + 无任何日志"，运维无从排查。

## 为什么标注为缺失（必须补）

1. **所有卡死类问题没有兜底诊断**：主线程卡住后没有任何机制记录"卡在哪"。bugs.txt 里的 bug 全靠"人肉复现 + 逐行读代码"定位，chunk-disappear 历史难题也是盲查——缺的就是卡死瞬间的现场快照。
2. **与已有审计条目联动**：SEC-001/SEC-002 的攻击后果因为没有 watchdog 而不可观测；修了 watchdog，攻击检测也变得容易（卡死堆栈直接指向解压/RCON 代码）。
3. Termux/Android 环境降频波动大，卡死比桌面更频繁，更需要现场诊断。

## 怎么做

实现极简版 watchdog（约 100 行，PHP 7.3 兼容）：

1. 新建 `src/pocketmine/utils/WatchdogThread.php`（继承 `Thread`）：
   - 构造时接收 `Server` 引用与阈值秒数（默认 30，配置键 `server.watchdog-threshold`，`server.watchdog=true` 开关默认开）。
   - 循环：每秒读取 `Server::$watchdogTimestamp`（主线程 tick 开始时更新，microtime）；与当前时间差超阈值 → 触发。
2. 触发动作：日志 `warning` 输出 "主线程疑似卡死 X 秒"；dump 主线程当前执行状态（pthreads 环境下主线程堆栈不可直接获取，退而求其次：记录最近一次 tick 的耗时、正在处理的阶段标记——在 `tick()` 的各阶段间更新一个 `$currentPhase` 字符串属性：console/network/scheduler/levels/players/save，watchdog 输出该标记即可定位卡在哪个阶段）；可选 `forceShutdown`（配置开关）。
3. 主线程集成：`tick()` 开头更新时间戳；各主要阶段之间更新 `$currentPhase`；`PocketMine.php` 启动流程里拉起线程，`Server::forceShutdown` 里停止。
4. 文档：pocketmine.yml 注释说明两个新配置键。

## 怎么测

- **触发验证**：临时在 `tick()` 里加 `sleep(60)`（调试模式），确认 30 秒后 watchdog 日志输出卡死警告 + 当前 phase 标记准确；移除调试代码后服务器自动恢复运行（watchdog 只是报告不误杀）。
- **误报验证**：正常大范围跑图 + 生成区块（单 tick 可达 200ms+）连续运行 1 小时，确认不触发（阈值 30s 有足够余量）。
- **联动验证**：复现 SEC-001 修复前的压缩炸弹攻击，watchdog 日志应指向 network phase——证明诊断链路有效。

# MISS-002 缺失：连接级限流（pre-login throttle） 【P1】

## 是什么

RakLib 层只有基础 session 管理，没有以下限流：同 IP 并发连接数上限、登录失败/畸形包限速、未完成握手连接的显式超时配置。SEC-001/SEC-003 已确认登录前即可攻击（无需认证），当前攻击成本几乎为零。

## 为什么标注为缺失（必须补）

1. **攻击面无前置防线**：解压炸弹（SEC-001）+ 畸形登录包（SEC-004）+ 假 JWT（SEC-003）全部发生在认证前，限流是唯一能让这些攻击"贵起来"的手段。
2. **无并发上限**：RCON 侧有 maxClients=50 的槽位机制，但游戏连接侧对同 IP 反复开连接没有任何约束——连接洪水直接消耗主线程 `processInterfaces` 时间。
3. 与 `RakLibInterface.php` 已有的攻击 IP 防火墙屏蔽机制（`Scaxe_Block_` netsh/iptables 规则）存在，但没有限流触发它的前置条件。

## 怎么做

在 `Player` 生命周期 + `RakLibInterface` 两层实现，全部配置化（pocketmine.yml）：

1. **同 IP 未登录连接上限**（默认 3）：`Server::getOnlinePlayers()` 过滤 `!$p->loggedIn && getAddress() === ip` 计数，`processLogin` 前超限则 close（提示 "connection throttled"）。注意 `Player.php:2397` `processLogin` 已有重复登录踢出逻辑，本条在其之前。
2. **握手超时**（默认 10s）：Player 构造/连接建立时记录时间戳，`onUpdate` 检查未完成 login 包且超时的直接 close（当前只有 RCON 槽位有 timeout，游戏连接没有）。
3. **畸形包计数**：`processBatch` 解压失败/超限（SEC-001 实现）、包 decode 抛异常时累加 per-player 计数器，60 秒内 ≥ N 次（默认 10）触发 IP 屏蔽（复用 `RakLibInterface` 的防火墙逻辑）并记录 warning。
4. 三项全部可在 pocketmine.yml 配置或关闭（`network.max-connections-per-ip` / `network.handshake-timeout` / `network.malformed-packet-limit`）。

## 怎么测

- **限流验证**：脚本用同一 IP 开 5 个并发连接不登录 → 第 4 个被立即断开并提示；不同 IP 不受影响。
- **握手超时验证**：建立连接后不发 LoginPacket，10 秒后被服务端主动断开，日志有记录。
- **畸形包封禁验证**：循环发解压炸弹 10 次 → 该 IP 被防火墙规则屏蔽（检查 `Scaxe_Block_` 规则生成）。
- **误伤验证**：正常客户端完整登录流程反复 20 次（模拟 NAT 后多玩家），不触发任何限流；同一 NAT 出口 4 人同时在线正常游玩。

# SEC-006 Shaped 配方缺格绕过：1 个材料合成完整产物（刷物品） 【P0】

## 是什么

`Player.php:4063-4083`（CRAFTING_EVENT_PACKET 的 ShapedRecipe 校验分支）中，合成格校验的 `elseif($ingredient !== null and $item->getId() !== 0)`（4078 行）存在逻辑洞：当某格是**必需材料**（ingredient 非 null）但客户端上报的物品是 AIR（id=0，或格子根本不上报）时，`$item->getId() !== 0` 为 false，整个 elseif 不成立直接跳过——**必需材料缺失不会导致 `$canCraft = false`**。

两个放大器：

1. `Player.php:4054-4056`：所有上报材料数量被强制 `setCount(1)`；且 4073 行 `deepEquals($item, ...)` 默认 `checkCount=false`，数量不参与匹配。
2. `Player.php:4119-4141`：材料扣除只针对客户端**实际上报**的条目（`$ingredients = $gridInput`），gridInput 非空时完全信任客户端；只有 gridInput 为空才走服务端配方兜底。扣除循环（4155-4169）按上报条目在背包里找货，缺格 = 不扣。

## 为什么

利用成本极低：已连接的任意玩家用改版客户端（或 0.15 窗口事务）在 CraftingEventPacket.input 里只上报 1 个格子的 1 个材料，其余必需格留空。以注册配方为例（`CraftingManager.php`）：

- 粘土块 = 4×粘土 → 上报 1 格 1 粘土 → **扣 1 粘土得 1 粘土块**，净赚 3；
- 荧石块 = 4×荧石粉 → 同理净赚 3；
- 工作台 = 4×木板 → 净赚 3；
- 所有非 Big 的 Shaped 配方全部命中。

守恒被打破，是本仓库目前发现的**最直接的可执行刷物品漏洞**。

## 怎么做

1. 形状校验改为服务端权威：`if($ingredient !== null and ($item->getId() === 0 or !$ingredient->deepEquals(...)))` → `$canCraft = false`。即 ingredient 非 null 时格子必须填且必须匹配，缺格即失败（一行修复）。
2. 材料扣除改为按配方 ingredient map（4124-4131 已有现成逻辑）而非客户端 `$gridInput`，与校验共用同一份数据源。
3. 顺带清理 4037-4046 的重复 null/big 检查（第二段永不触发，死代码）。

## 怎么测

- 回归基线（HYG-004 的快照测试）覆盖：完整材料合成 → 成功且扣料正确；缺 1 格必需材料 → 拒绝并 sendContents。
- 手工脚本：模拟 CraftingEventPacket（粘土块配方，input 只填 1 格）断言背包无粘土块产生。
- 0.15 窗口事务路径与旧协议路径各测一遍。

# SEC-007 NBT 标签数量无上限：解压放大成 GB 级对象（OOM 崩服） 【P1】

## 是什么

NBT 二进制解析器（`NBT.php`）对**单项**做了封顶——`MAX_READ_DEPTH = 64`（73-74 行）、IntArrayTag 32768、ByteArrayTag 2MB、ListTag 16384、字符串 65535——但对**标签总数**没有任何限制。与 SEC-001 的 64MB 解压上限组合后：64MB 数据可塞约 2000 万个最小 Tag（TAG_Byte ≈ 3-4 字节/个），每个是 PHP 对象（实际 ~400-600 字节），峰值内存 **10GB+**，直接 OOM 崩服。深度限制只防递归不防广度。

## 为什么

这是 SEC-001 的第二级放大：SEC-001 防的是解压耗时，本条防的是解压后对象的内存放大。单进程同步处理，一个 ~几 KB 的压缩包就能打崩全服，比 SEC-001 的 CPU 炸弹更快。parseJSON 文本解析器（`NBT.php:188-437`）另有独立问题：递归下降无深度计数（`MAX_READ_DEPTH` 不适用），`[[[[...` 千层嵌套硬 crash——当前唯一入口 `/give` 需 op，故并入本条备注，插件若用它解析客户端数据即升 P0。

## 怎么做

1. `NBT::readTag` 增加每包标签计数上限：解析器实例加 `$tagCount` 字段，`enterDepth` 或每次 readTag 时自增，超过上限（建议 100000，正常物品 NBT 几十个）抛 `RuntimeException`，由 `Network.php:270` 现有 `\Throwable` 兜底丢包。
2. `parseJSON` 的 parseCompound/parseList/readValue 递归链加深度计数参数，超 128 抛异常。
3. fail-fast：`DataPacket::getSlot()` 收到的 NBT 预解析一次（当前延迟到 `getNamedTag()` 才爆，异常时点不可控），解析失败即踢人。

## 怎么测

- 构造压缩包：5 万个 TAG_Byte 的 compound，解压后处理，断言被拒绝且服务器存活、内存平稳。
- 正常物品（附魔书、地图、盾牌等带 NBT 物品）回归不受影响。
- `/give @p diamond 1 {ench:[...]}` 与超深嵌套 `[[[[...` 断言优雅报错。

# SEC-008 创造模式 MOB_EQUIPMENT 信任客户端物品 【P2】

## 是什么

`Player.php` MOB_EQUIPMENT_PACKET 处理中：`if($this->isCreative()){ $item = $packet->item; $slot = Item::getCreativeItemIndex($item); }` ——创造模式直接采信客户端上报的 Item（含 NBT/附魔/count），`Item::getCreativeItemIndex`（`Item.php`，`equals($d, !$item->isTool())`）只按 id+damage 匹配忽略 NBT。随后 `$this->inventory->setItem($packet->selectedSlot, $item)` 把客户端原始物品写入背包。

## 怎么测

# SEC-011 BanEntry::hasExpired 副作用错乱：所有限时封禁即刻失效 【P1】

## 是什么

`BanEntry.php:73-82`：

```php
public function hasExpired(){
    $now = new \DateTime();
    if($this->expirationDate === null){
        return false;
    }else{
        $this->expirationDate = $now;   // 把过期时间覆写为"现在"
        return $now;                    // 返回 DateTime 对象，恒为 truthy

```

## 是什么

## 怎么测

- 非 OP 执行 /oplist → 权限拒绝，无日志异常。
- player-tp=1：非 OP /tp 自己 ✓、/tp 别人 ✗、/gm 改别人 ✗。

## 怎么测

- 连发 USE_ITEM → 仅按间隔生效，不踢人、不即时回血。
- 正常动画进食流程回归；创造吃金苹果不消耗。

# SEC-015 BanList 持久化非原子 + 损坏行 TypeError 炸服 + 分隔符无转义 【P2】

## 是什么

`BanList.php:131-165` 与 `BanEntry.php:92-135` 三个持久化缺陷：

1. `save()` 用 `"w"` 模式 fopen 直接截断原文件再逐条写——中途 fatal/断电即**全部封禁记录丢失**；无 temp+rename、无 flock（仓库内 Config.php/Utils.php 已有原子写先例可复用，同 MISS-004）。
2. `load()` 无 try/catch：损坏行（如 `name||src|exp|r`）经 `fromString` → `setCreated(false)`，而 `setCreated(\DateTime $date)` 带类型 hint → 未捕获 TypeError——`/reload` 时直接炸服。
3. 格式用 `|` 分隔且无转义：reason 含 `|` 被截断、含换行（RCON 可注入，见 BUG-013 第 13 条）会把下一行解析成垃圾条目。

## 为什么

封禁数据是安全审计的最后一道防线，其持久化却是"最脆弱写法"：丢档、炸服、格式破坏三连。与 SEC-011/BUG-009 同属封禁系统整条链路的质量塌方（命令参数错 → 逻辑错 → 持久化错）。

## 怎么做

save 改 temp+rename 原子写；fromString 每字段 instanceof 校验，坏行跳过 + 日志告警；写入前对 reason 做 `|`/换行转义（或整体迁 JSON 格式）。建议与 SEC-011/BUG-009 一起作为"封禁系统专项"一次修完。

## 怎么测

- 构造含 `|`、换行的 reason → 保存/加载 roundtrip 无损。
- 手工写入损坏行 → reload 跳过该行并告警，服务器正常启动。
- 写入中断模拟（kill 进程）→ 原文件完好。

# SEC-020 RakLib 调用不存在的 Session::isActive()：全服断网 【P0】

## 是什么

`src/raklib/server/SessionManager.php:271-279`（checkSessions 第二段清理循环）：
```php
if(count($this->sessions) > 4096){
    foreach($this->sessions as $i => $s){
        if(!$s->isActive()){   // ← Session 类没有这个方法
```
Session.php 只有私有属性 `$isActive`（:80）和 `isTemporal()`（:400），**没有 isActive() 方法**（全 raklib/server 无 `function isActive` 定义，已 grep 验证）。会话数一旦超过 4096，第二段循环必抛 `Call to undefined method`，沿 `getSession → receivePacket → tickProcessor → SessionManager::run` 一路上抛 → **RakLib 线程死亡** → 主线程 `RakLibInterface::process()` 检测 `isTerminated()` 后 `Network::emergencyShutdown()`（Network.php:158-175）→ 全部玩家掉线，只能重启。

## 为什么

触发门槛极低且无需肉机：单 IP 用 4096 个源端口各完成 4 包握手（约半分钟，packetLimit 0.75 衰减折算 ~600 pkt/s），持续保活（CONNECTED 后 isTemporal=false，第一段清理不删），再从新端口发任意池内包即触发。一段代码从未被测试过（该方法不存在，说明这段分支历史上从未执行成功过）。

## 怎么做

在 Session 增加 `public function isActive(){ return $this->isActive; }`；或第二循环改用 `$s->isTemporal()` / 活跃时间判断。一行修复。

## 怎么测

- 本地模拟 4097 个会话（或临时把 4096 阈值调低）→ 第二循环执行不再抛 Error。
- 正常会话保活/超时清理回归。

# SEC-021 RakLib 握手零校验：UDP 源伪造 + 反射放大 【P1】

## 是什么

- OPEN_CONNECTION_REQUEST_1/2、CLIENT_CONNECT、UNCONNECTED_PING 的 decode 全部 `offset += 16` 跳过 Magic，从不与 RakLib::MAGIC 比对。
- 全程无 challenge/cookie（`useSecurity` 读了没人看）。
- UNCONNECTED_PING 对最短 1 字节包回 ~100B 完整 MOTD（SessionManager.php:187-196），放大 ~100 倍且方向由攻击者指定。

## 为什么

UDP 源地址可伪造：攻击者以受害者 IP 发 4 个握手包即可让服务器为受害者建 Session 并回调 openSession 创建 Player（RakLibInterface.php:112-122），应答全部打到受害者；UNCONNECTED_PING 可作反射放大器。这是整个 RakLib 攻击面的根因（SEC-023 的武器化前提、P2-4 的 Player churn 前提）。

## 怎么做

①decode 比对 MAGIC 不符即丢弃；②OPEN_CONNECTION_REQUEST_2 引入 cookie/challenge（REPLY_1 带随机数，REQUEST_2 必须回带）；③UNCONNECTED_PING 至少要求 9 字节 + magic 正确。

## 怎么测

- 伪 magic 握手包 → 丢弃无会话；正常客户端回归。
- 1 字节 ping → 无响应。

# SEC-022 ACK/NACK 出站无上限 + NACK 无限重传 【P1】

## 是什么

- `Session.php:483-493`：攻击者每发一个 seqNumber=windowEnd 的 DATA_PACKET 即把窗口推进 2048 并生成 2048 条 NACK 记录（编码 ~7B/条 → 单包应答 ~14KB）。配合 packetLimit 150/tick，稳态 ~40MB/s 应答洪流打到（可能伪造的）源地址。入站 AcknowledgePacket 有 cnt<4096 限制，出站零限制。
- `Session.php:526-540`：NACK 重传限制形同虚设——`recoveryRetry` 以 seq 为键但重传时 `seqNumber` 换新号 + 下一行立刻 `unset($this->recoveryRetry[$seq])`，计数器从不跨事件存活 → 同一包可被 NACK 无限次触发重传；且换 seqNumber 导致客户端把同一业务包重复投递（有序通道重复执行）。

## 为什么

对真实客户端也是每包 100 倍级上行放大；配合 SEC-021 源伪造形成持续重传洪流。代码注释声称"防放大"但逻辑无效，属"写了防护但防护从未生效"的典型。

## 怎么做

①diff > 窗口/4 直接 disconnect("invalid seq gap")，NACK 每 tick 限幅；②重试计数挂到包对象自身（$pk->retryCount），超限丢包；③NACK 重传保持原 seqNumber（与超时路径 194-201 行一致）。

## 怎么测

- 伪造大 gap DATA_PACKET → 连接被断而非 14KB 应答。
- 反复 NACK 同一 seq → 重传计数生效，超限丢包；业务包不重复投递。

# SEC-023 ipSec 自动封禁武器化：伪造源 IP 封禁无辜玩家 【P1】

## 是什么

`SessionManager.php:130-139`：限流基于 UDP 源地址（可伪造）。攻击者以受害者 IP 伪造 150 包/tick 垃圾流量 → `blockAddress(受害者)` 300 秒 → 真实玩家被踢且无法重连，循环发送即持续封禁。开启 netshBlock 时（RakLibInterface.php:152-159）还会写入 Windows 防火墙 `Scaxe_Block_<ip>` 规则——escapeshellarg 已防注入，但规则**永不删除**（raklib block 超时只清内存表），且伪造 IP 可塞任意"IP"永久规则。

## 为什么

把防御机制（自动封禁）变成了攻击武器（定向断联工具），且 netsh 残留规则重启后继续拦截无辜地址。MISS-002 计划复用的 Scaxe_Block_ 防火墙机制必须先修此处。

## 怎么做

①自动封禁只对完成过握手的地址生效，未握手源只 drop 不 block；②netsh 规则在解封时同步 delete；③落防火墙前 filter_var 校验 IP（与 MISS-002 联动设计）。

## 怎么测

- 用未握手源刷包 → 仅丢弃无封禁；握手后超限 → 封禁且解封后 netsh 规则消失。

# BUG-022 McRegion 损坏隔离失败路径：崩服循环 【P1】

## 是什么

`src/pocketmine/level/format/mcregion/McRegion.php:216-235`：region 损坏时尝试隔离（copy 到 corrupt-quarantine/），但 `@copy` 失败（磁盘满/只读 FS/Android 权限）时 `return false` → chunk 不进 $this->chunks。随后 `Level::setBlock`（Level.php:1647）/`getBlockIdAt`（2280-2281）对 `getChunk(...,true)` 返回 null 直接解引用 → fatal；`Level::loadChunk`（3253-3256）抛 InvalidStateException 沿 doTick 冒泡 → 崩服且玩家每次走进该区块都崩（崩服循环）。

## 为什么

隔离机制本意是容错，但失败分支把"可容错的坏 region"升级成"必崩的死循环"。Android 设备存储紧张时磁盘满是现实场景。

## 怎么做

①隔离失败仍返回空 chunk 并把损坏条目 removeChunk 出索引；②setBlock/getBlockIdAt 对 null chunk 防御；③loadChunk 的 throw 改记日志返回 false。

## 怎么测

- 构造坏 region + 只读目录 → 服务器存活、玩家收到空区块而非崩服。

# BUG-023 region GC 后 saveChunk 崩服 【P1】

## 是什么

`McRegion.php:260-268` saveChunk 直接 `$this->getRegion(...)->writeChunk(...)` 不 loadRegion；而 doGarbageCollection（195-203）会 close+unset 300 秒未用的 region。区块加载超 300 秒且 region 无读写 → GC 关闭 region → unloadChunks → BaseFullChunk.php:385 saveChunk → 对 null 调 writeChunk → fatal。

## 为什么

长寿命区块 + 低写入场景（挂机玩家常驻区块）满足触发条件；`Level::saveChunks` 侥幸安全仅因它先调了 setChunk（内部 loadRegion）。与 BUG-022 同属 provider 层 null 防御缺失。

## 怎么做

saveChunk（writeChunk 前）加 `loadRegion($x >> 5, $z >> 5)` 或 null 检查；GC 关闭 region 前检查该 region 内是否仍有已加载区块。

## 怎么测

- 加载区块后把 region lastUsed 手工调旧 → 触发 GC → unload 保存不崩。

# SEC-024 splitPacket 重组三洞 【P2】

## 已验证安全（第六轮排除项）

### 区块存储/生成器
- **region 保存写序**：先写数据扇区再写 location index，掉电时旧索引指向旧数据，无索引指向半截新数据的窗口。
- **mcregion 空文件保护存在**（anvil 缺失见 BUG-025）。

- **生成/population 任务异常处理**：onRun try/catch + 失败释放 3×3 population 锁 + registerGenerator 重建 worker，无死锁。
- **跨线程数据传递**：deferred tiles 用 JSON 字符串规避 pthreads 数组陷阱；Generator 设置 unserialize 带 allowed_classes=false。

### RakLib
- **ACK/NACK 入站解码上限**（cnt<4096、range≤512、feof 守卫）——出站无限制是 SEC-022，入站安全。
- **MTU 钳制** max(400, min(mtu,1432))——碎片风暴已防。
- **线程边界**：RakLib↔主线程全部经 Threaded 队列，无跨线程共享可变状态；主线程解码异常 try/Throwable 隔离。
- **收包循环限幅**每 tick ≤5000 包；会话表 4096 上限 + temporal 优先清理（第二循环方法缺失是 SEC-020）；登录前 Player 10s 强踢；封禁表超时清理正确。
- **bandwidth 统计 unserialize**：输入由 RakLib 线程内部 serialize 生成非用户可控。
- **netsh 命令注入**：escapeshellarg 已防（规则残留是 SEC-023 的另一面）。
- **fe/8e 前缀分发**：strlen 先检，无越界。
- **EncapsulatedPacket::fromBinary 越界**：substr 钳制 + 空 buffer break，仅 notice 问题（并入 SEC-020 修复批次的降噪）。

> 第六轮核心洞察：**RakLib 是整个服务器唯一"从未被攻击者视角看过"的层**。玩家面系统（合成/战斗/容器）至少挨过打有补丁，而 RakLib 的握手连 magic 都不校验、重传防护写了但从未生效、自动封禁能被武器化——因为它默认自己运行在内网。老协议分叉直接暴露公网时，网络层比游戏逻辑层更脆。另外 Session::isActive 这种"调用了不存在方法"的 P0 说明 checkSessions 的清理分支从未成功执行过——超过 4096 会话的服务器当前版本根本无法存活，这本身就是最好的"证明无人在大服跑此分叉"的证据。
